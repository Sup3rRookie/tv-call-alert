# RT1 protocol

Two parties share a 16-byte pairing seed `P`: the TV app (which generates it) and one phone.
All traffic goes through a public ntfy relay (`https://ntfy.sh`), so every message is signed
and carries no personal data.

## Pairing code

`P` is shown on the TV as RFC 4648 base32 without padding: 26 characters, grouped in fours
with hyphens (`ABCD-EFGH-IJKL-MNOP-QRST-UVWX-YZ`). Parsers ignore spaces, hyphens and case,
and reject anything that is not exactly 26 base32 characters with zero padding bits.

The TV shows the code prefixed with the slot number, as one pairing string:
`<slot>-<code>`, for example `1-ABCD-EFGH-IJKL-MNOP-QRST-UVWX-YZ`. The phone reads the
first character as the slot (`1` to `4`) and the rest as the seed code.

## Derived values

`HMAC` is HMAC-SHA256. Labels are ASCII.

| Value | Derivation |
|---|---|
| `kAuth` | `HMAC(P, "rt1/auth")`, signs phone to TV messages |
| `kAck` | `HMAC(P, "rt1/ack")`, signs TV to phone acks |
| `topicDown` | `"rt" + hex(HMAC(P, "rt1/down"))[0..40]`, phone publishes, TV subscribes |
| `topicAck` | `"rt" + hex(HMAC(P, "rt1/up"))[0..40]`, TV publishes, phone subscribes |

## Phone to TV

One line of printable ASCII, at most 200 characters:

```
RT1|<type>|<slot>|<ts>|<nonce>|<ref>|<mac>
```

| Field | Rule |
|---|---|
| type | `alert`, `cancel` or `ping` |
| slot | one digit `1` to `4`, must be the slot whose `topicDown` it arrived on |
| ts | 10-digit unix seconds, phone clock, no leading zero |
| nonce | 22 base64url characters (16 random bytes, no padding) |
| ref | for `cancel` the nonce of the alert to cancel, otherwise `-` |
| mac | 43 base64url characters: `HMAC(kAuth, "RT1|type|slot|ts|nonce|ref")`, no padding |

Published with `POST https://ntfy.sh/<topicDown>` and the line as the request body.

Every new message from a phone must carry a `ts` strictly greater than the one before it:
`ts = max(now, lastTs + 1)`. The phone keeps `lastTs` across page reloads (it is not secret).
A retry re-sends the identical line and is exempt.

## TV to phone

```
RA1|<status>|<slot>|<ts>|<ref>|<mac>
```

`ts` is unix seconds on the relay clock, `ref` is the nonce of the message being answered,
`mac` is `HMAC(kAck, "RA1|status|slot|ts|ref")` as 43 base64url characters.

| Status | Meaning |
|---|---|
| `shown` | the card is on screen |
| `dismissed` | someone pressed OK or Back on the remote |
| `expired` | the card timed out with nobody dismissing it |
| `cancelled` | the phone's cancel removed the card |
| `asleep` | the TV screen is off, no card was shown |
| `stale` | rejected: timestamp too old, too far ahead, or older than one already accepted |
| `limited` | rejected: too many alerts in a short time |
| `failed` | the TV could not draw the card (permissions missing) |
| `pong` | answer to `ping`: the TV is online |

The phone must verify the mac and that `ref` is a nonce it sent before trusting an ack.
Acks are sent only for messages whose mac verified.

## TV acceptance order

1. length at most 200, printable ASCII only, exact grammar
2. topic maps to a paired slot and equals the slot field
3. mac verifies (constant time)
4. `relayNow - ts` within `[-30, +60]` seconds
5. nonce not seen in the last 120 seconds
6. `ts` strictly greater than the highest `ts` already accepted for the slot. That mark is
   persisted, so a relay-cached copy of an accepted message is rejected even after the TV app
   restarts. Rejected silently as a replay, with no ack.
7. rate limit: alerts 10 s apart, 3 per 5 minutes, 30 per day; pings 2 s apart; cancels unlimited

`relayNow` comes from the `time` field of live relay events, not the TV's own clock.

A phone retry re-sends the identical line. The TV treats it as a replay and, if that alert's
card is still up, answers `shown` again.
